# RelayCrew growth playbook

The goal is a completed first use, then repeat use, useful reports, and contributions. Stars are a secondary signal. This plan contains positioning and distribution hypotheses, not measured search volumes, rankings, conversion rates, or guaranteed growth. Public copy stays in English. No posts, messages, paid campaigns, or directory submissions have been sent.

## Conversion path

1. A visitor recognizes the overlapping-work problem in the first screen.
2. They run a local example without signing up or installing dependencies.
3. They install the skill in an existing coding assistant.
4. They complete a real task and see the acceptance checks.
5. They share a minimal workflow or failure report; a star is an optional way to find the project again.

Measure this without invasive telemetry: release-asset downloads are a rough proxy, not installs; repository traffic is not completed usage; stars are not retention. Use voluntary workflow reports for actual outcomes. If a future site uses analytics, disclose it and report the collection method.

## Platform distribution

### GitHub: make trying the product the main action

- **Message:** “Parallel AI coding. Clear ownership. Try the offline lockfile example, then use the skill on a real repository task.”
- **Format:** clear repository description and topics, a short README demo, small versioned ZIP, release notes, and reproducible workflow reports.
- **Avoid:** empty contribution activity, star exchanges, inflated benchmark claims, confusing the planner with the whole skill, and asking for stars before showing value.
- **CTA:** run the example; return one minimal workflow report if it helps or fails.
- **Next action:** use the published example and release, then link one real team trace from the README. Keep roadmap issues tied to observable problems rather than creating a large decorative backlog.

### Hacker News: a maker's own account and own words

- **Recommended message content:** explain the real coordination problem you personally encountered, show the runnable artifact, describe the small-team tradeoff, and state what the test did and did not show. The maker must write the final submission and comments themselves.
- **Format:** a substantive, runnable Show HN with direct access and no signup barrier, after the maker has tried it personally and can stay to discuss it. A list of instructions alone is a weak launch; lead with the working planner and a real code-change demonstration.
- **Avoid:** posting this generated text, automated posting, requesting votes, repeated minor-version launches, or presenting a landing page as a runnable product. HN explicitly requires human-written posts and comments. [HN guidelines](https://news.ycombinator.com/newsguidelines.html), [Show HN guidelines](https://news.ycombinator.com/showhn.html).
- **CTA:** ask for specific technical criticism about the demonstrated tradeoff, in the maker's own words.

### Reddit: one relevant community, one useful example

- **Draft message:** “I made RelayCrew to make file ownership and handoffs explicit when several coding agents work on one change. Here is a short example where two tasks share a lockfile, so the plan separates them while unrelated docs work continues. It is an early open-source skill with an offline planner. What would make this useful in your actual workflow?”
- **Format:** a self-contained text post or short clip in a community that currently allows project showcases. Include the example before the repository link and disclose that you maintain the project. Recheck the selected community's current rules before posting.
- **Avoid:** copying the same promotion across subreddits, unsolicited messages, vote coordination, and hiding a commercial or maintainer relationship. Reddit's policy treats repeated unsolicited promotion as spam. [Reddit spam policy](https://support.reddithelp.com/hc/en-us/articles/360043504051-Spam).
- **CTA:** ask for one real conflicting-task example, not an upvote.

### Dev.to: teach the problem, then offer the tool

- **Draft opening:** “Two coding agents can make progress independently and still leave one difficult integration problem. This walkthrough makes the shared contract and file ownership explicit, then shows which work can run together and which must wait.”
- **Format:** an original tutorial with runnable JSON, expected output, a short trace, and a link to the exact release. Include an AI-assistance disclosure for drafted material and personally verify every command before publication. [DEV code of conduct](https://dev.to/code-of-conduct).
- **Avoid:** a feature-list advert, copied source material, unlabeled generated content, and claiming a speedup from a single successful run.
- **CTA:** reproduce the example and adapt it to one of your own workstreams.

## Benchmarks: demonstrate, do not assume

### Experiments

1. **Solo baseline vs RelayCrew auto:** small dependent change, medium independent change, and conflict-heavy change. Determine when coordination earns its overhead.
2. **Explicit team vs unstructured team:** same host and worker ceiling, with and without the skill; test handoff and integration outcomes.
3. **Recovery experiment:** inject the same reproducible prerequisite failure; measure held dependent tasks, unrelated progress, and repair work.
4. **Ownership experiment:** include shared lockfiles, directory reads, generated files, and separate files. Count actual overlaps, not merely declared ones.

### Method

Use clean identical repository snapshots, frozen acceptance tests, the same model/version, tool permissions, worker ceiling, and task prompt except for the skill invocation. Randomize run order; use at least five matched repetitions per task family as an initial exploratory study and expand before broad claims. Do not let baseline runs see prior solutions. Fix the task set before comparing. Record all failures, retries, manual intervention, and censored/time-limited runs.

| Metric | Definition |
| --- | --- |
| Acceptance pass rate | Runs satisfying all frozen acceptance checks / all attempted runs |
| Time to verified result | Start of the task to final passing integrated checks, including repair and handoff time |
| Worker write overlap | Concurrent conflicting writes observed from actual file/tool traces |
| Coordination failures | Missed interface fact, premature dependent dispatch, or ownership violation with trace evidence |
| Repair effort | Additional edits, tool calls, and elapsed time after first integration failure |
| Useful throughput | Accepted tasks per fixed wall-clock budget, not generated lines or commits |
| Context and usage | Actual reported input/output usage per full run, summed across workers, where available |
| Cost | Actual billed or documented usage-based cost under the stated plan; report unavailable data as unavailable |
| Human interruption | Number and duration of required interventions |

Publish per-run values, median and spread, pass rates, and the exact environment. For paired comparisons report the paired difference and uncertainty, not only the best run. A speedup that lowers acceptance quality is not a win. Existing exploratory coding runs are feasibility evidence and do not establish comparative speed, cost, or productivity gains.

## Seven-day plan, ordered by expected return on effort

Expected return below is a qualitative prioritization hypothesis. There is no acquisition dataset yet.

1. **Working first use:** keep the release, install path, three runnable planner examples, and acceptance checks correct. Success: a new user can reproduce the example and load the skill without maintainer intervention.
2. **One real coding demonstration:** record the event-report workflow and its limitations. Success: viewers can reach the same acceptance checks from the fixture.
3. **README and evidence:** lead with the problem, the demo, and the exact capability limits. Success: early testers can explain when they would use it.
4. **Five voluntary workflow observations:** seek feedback through the author's existing, appropriate channels; no unsolicited campaigns. Success: repeated problems emerge from concrete reports.
5. **One substantive tutorial:** teach the shared-lockfile or failure-hold pattern. Success: useful questions and reproducible adaptations, not just impressions.
6. **Choose one showcase channel:** submit only when the maker has personally used it, is available to discuss it, and current platform rules allow the format.

## Thirty-day plan

1. Fix repeated installation or coordination failures before adding features.
2. Collect matched benchmark runs across the three task families; publish raw results even if the skill does not improve them.
3. Validate Claude Code and another host through real contributed traces; update the compatibility matrix instead of assuming parity.
4. Curate three to five useful workflows, each with explicit ownership and acceptance checks.
5. Publish two problem-focused articles based on observed questions. Build a small landing page only after the message is stable.
6. Try a single relevant directory submission after checking its current requirements; avoid mass submissions.
7. Review activation: how many voluntary first-use reports become second-use reports? Treat missing data honestly.

## Ninety-day plan

1. Keep, narrow, or stop features based on repeat use and real integration outcomes. If the planner carries the value, position it clearly rather than hiding it behind agent language.
2. Add maintainers only through real contributions; document release and compatibility responsibilities.
3. Improve a proven integration path or package a supported plugin if users request it. Public directory review remains a separate platform process.
4. Expand benchmark coverage and host versions without converting exploratory results into universal claims.
5. Build content around the top recurring problems with evidence-rich example pages. Retire thin or unused material.
6. Consider a larger product only if users repeatedly need state enforcement or orchestration that a lightweight skill cannot provide. Preserve the small skill as an honest, useful unit.

## First growth experiments

Targets below are decision thresholds for planned experiments, not promised outcomes or current traction.

| Priority | Experiment | Smallest action | Useful decision signal |
| --- | --- | --- | --- |
| 1 | Can a new developer reach a first result? | Observe 5 voluntary first-use attempts without explaining the README live | At least 4 can run the demo; fix every repeated install blocker before promotion |
| 2 | Does the ownership problem resonate? | Show the lockfile clip and the general team clip to relevant existing contacts who opt in | Which produces specific examples of the same pain, not just compliments? |
| 3 | Does the skill survive a real task? | Collect 5 minimal workflow reports across distinct repositories | At least one repeat-use report and a clear account of the benefit or failure |
| 4 | Which technical channel brings useful feedback? | Publish one verified tutorial or approved showcase through the maker | Track voluntary reports and reproducible questions attributable to that post |
| 5 | Is the recovery feature distinctive? | Compare matched failure fixtures with and without the workflow | Fewer premature dependent dispatches without a worse acceptance rate |

At 30 days, the ambition is evidence of repeat use, three genuinely reusable community workflows, and at least one outside contribution that fixes a real problem. At 90 days, decide from the evidence whether to deepen the coordination workflow, emphasize the planner, or narrow the project. Do not substitute a larger star target for product learning.
